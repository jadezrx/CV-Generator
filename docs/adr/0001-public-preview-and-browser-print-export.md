# Public preview at `/`, management moves to `/manage`, PDF export via browser print

`/` currently renders the portfolio but mixes it with Supprimer buttons — not something you'd share with a recruiter. We need a clean public view, a way to edit existing entries, and a PDF export.

Zero-client-JS was chosen first as a genuine trade-off among three real options (strict zero-JS, minimal vanilla JS, a full framework) — that analysis wasn't wrong, and it held until a new requirement surfaced: the PDF export trigger needed to be a discoverable button, not a hidden keyboard shortcut (Ctrl+P) the user has to already know about. That requirement, not a flaw in the original reasoning, is what narrowed the constraint to "minimal vanilla JS (no framework), scoped to the export button only." Server-side HTML→PDF libraries (WeasyPrint, wkhtmltopdf) still need system packages (Cairo, Pango, ...) that `pip` cannot install, and this repo deploys to Render as a native Python service with no `Dockerfile` — so a server-rendered PDF pipeline would still force a move to a Docker-based deploy just for this feature.

**Decision**: `/` becomes the public, read-only, clean portfolio view — no edit/delete affordances. `/manage` takes over today's `/` content unchanged in shape (entry lists with Modifier/Supprimer for existing entries). `/form` keeps its existing, separate role as the dedicated Create page — it is not merged into `/manage`. Both `/form` and `/manage` sit behind the same HTTP Basic Auth gate (ADR-0003). PDF export has no dedicated route or server-side rendering: a visible "Exporter en PDF" button on `/` calls `window.print()` (minimal inline vanilla JS, e.g. `onclick="window.print()"`), against a `@media print` stylesheet that hides non-content chrome. The browser's native print-to-PDF does the actual rendering.

**Considered and rejected**: server-side WeasyPrint/wkhtmltopdf (infra migration cost to Docker), ReportLab (hand-coded layout, a second source of truth for styling diverging from the HTML/CSS template), no button at all — just telling users to press Ctrl+P (rejected on revision: less discoverable than a real button; the minimal-JS cost of a single `onclick` was judged worth it).
